## 2026-11-03 — DataGrid server mode (F6)

- **Built:** `server={{ query, onQueryChange, rowCount, loading }}`. The grid shows one page (`data`), and sorting, column filters, search and paging become one plain `DataGridQuery` (`pageIndex` 0-based, `pageSize`, `sort`, `filters`, `search`) for the app to fetch with. Added: a `Pagination` bar (compact, rows per page), "51–100 of 12,450 rows", `aria-busy` + "Loading…", `aria-rowcount` = server total and `aria-rowindex` counting across pages. New guide `docs/data-grid-server.md` with a Spring recipe.
- **Remember (the prediction): narrowing resets the page.** Any change to _which_ rows match (sort, filter, search) goes back to `pageIndex: 0` (`narrowQuery`). On page 40 with a filter that now matches 120 rows, page 40 doesn't exist: the grid would show "No rows" while 120 rows match. Paging and page size are the only changes that keep a position.
- **Remember: `manualSorting` / `manualFiltering` only switch the browser's work off.** They never call your backend. The grid describes the query; the app (TanStack Query, `useEffect` + `AbortController`, anything) fetches. It's the same split as `onSave`: the library stays backend-neutral.
- **Remember: debounce the request, not the typing.** The search box updates on every key; the query changes 300ms after the last one, so "rock" is one request, not four. Also: `placeholderData: keepPreviousData` keeps the old page visible while the next loads, so the table doesn't flash empty.
- Docs: https://tanstack.com/table/latest/docs/guide/pagination#manual-server-side-pagination
